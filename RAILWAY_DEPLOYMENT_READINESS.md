# Railway Deployment Readiness

Date: 2026-06-02

Target architecture:

- Frontend: Vercel
- Backend API: Railway
- Worker: Railway
- PostgreSQL: Railway managed PostgreSQL
- Redis: Railway managed Redis

## Verdict

RepoMindAI cannot be declared deployable on Vercel + Railway today.

The backend image now builds, Railway-style database and Redis environment variables are accepted, and separate API/worker start commands exist. The remaining launch blocker is artifact locality: the worker writes Chroma indexes and report files to its local filesystem, while the API later reads those same local paths to serve reports and answer chat. The repository has no shared artifact storage, object storage backend, Chroma server, or database-backed report/vector artifact storage that proves a separate Railway API service can read artifacts generated by a separate Railway worker service.

## Architecture Audit

### Backend API

FastAPI is created in `backend/repomind/main.py` and exposes `/health` for platform health checks. Railway backend config now starts the API with Railway's `$PORT`:

- `Dockerfile.backend`
- `deploy/railway.toml`

The Docker image installs runtime and analysis dependencies with `.[analysis]`, not the local LLM extras. This keeps Bandit, Semgrep, Tree-sitter, Chroma, Redis/RQ, PostgreSQL, and FastAPI dependencies while avoiding the previous native LLM build failure.

### Worker

Analysis jobs are queued through RQ when `REPOMIND_ANALYSIS_QUEUE_BACKEND=rq` and Redis is configured. The worker entrypoint is `python -m repomind.worker` and consumes the `repomind-analysis` queue:

- `backend/repomind/core/jobs.py`
- `backend/repomind/worker.py`
- `deploy/railway.worker.toml`

### PostgreSQL

The SQLAlchemy store is primary metadata storage. Production rejects missing database URLs and rejects SQLite:

- `backend/repomind/core/config.py`
- `backend/repomind/core/store.py`
- `backend/repomind/db/alembic/env.py`

The config now accepts Railway's unprefixed `DATABASE_URL` as well as `REPOMIND_DATABASE_URL`.

### Redis

RQ uses Redis from settings. The config now accepts Railway's unprefixed `REDIS_URL` as well as `REPOMIND_REDIS_URL`:

- `backend/repomind/core/config.py`
- `backend/repomind/core/jobs.py`

### Chroma Persistence

Chroma uses an embedded local persistent client:

- `backend/repomind/rag/indexer.py`

Railway configs set `REPOMIND_CHROMA_DIR=/data/chroma`, but the repository does not define or prove a shared persistent artifact store between the API and worker services.

### File Storage

Reports are generated as local files under `settings.reports_dir / "generated" / repo_id` and served later through `FileResponse`:

- `backend/repomind/reports/generator.py`
- `backend/repomind/main.py`

Railway configs set report/index/upload directories under `/data`, but separate API and worker services still need a shared artifact mechanism for report downloads, exports, and chat retrieval to work after background analysis.

### OAuth Callbacks

OAuth routes exist:

- `/auth/github/login`
- `/auth/github/callback`
- `/auth/google/login`
- `/auth/google/callback`
- `/github/app/install-url`
- `/github/app/callback`

The callback base uses `REPOMIND_PUBLIC_APP_URL`. CORS uses `REPOMIND_FRONTEND_ORIGIN`. These must be set to the final Vercel frontend URL.

### Frontend

The frontend now accepts both:

- `NEXT_PUBLIC_API_BASE`
- `NEXT_PUBLIC_API_BASE_URL`

This fixes the mismatch between existing deployment references and `frontend/lib/api.ts`.

## Blockers

### P0: API and worker do not have a proven shared artifact store

Root cause:

- Worker analysis writes reports to local paths in `backend/repomind/reports/generator.py`.
- Worker indexing writes Chroma collections under `settings.chroma_dir` in `backend/repomind/rag/indexer.py`.
- API report downloads read local paths from metadata in `backend/repomind/main.py`.
- API chat retrieval reads embedded Chroma from its own `settings.chroma_dir`.
- `backend/repomind/db/models.py` stores artifact paths, not artifact bodies.
- The repository contains no object storage backend, shared Chroma server configuration, or database-backed artifact body storage.

Implementation completed:

- Backend and worker Railway configs now point all local artifacts to `/data`.
- This is necessary but not sufficient for two separate services unless the deployment provides a shared artifact layer.

Evidence:

- `generate_reports()` writes files to local `settings.reports_dir`.
- `download_report()` calls `Path(...).exists()` and returns `FileResponse(path)`.
- `_collection()` creates `chromadb.PersistentClient(path=str(settings.chroma_dir))`.
- `ArtifactRecord` stores `path`, not content.

Remaining gap:

- A Vercel + Railway deployment with separate API and worker services needs one of:
  - a shared artifact storage service used by both API and worker,
  - a remote Chroma service plus object storage for reports,
  - database-backed report bodies and a vector backend reachable by both services,
  - or a topology change that keeps API and worker artifact access in the same service/filesystem.

### P0: Railway managed PostgreSQL and Redis are not live-validated in this repository

Root cause:

- No real Railway service credentials are present in the repository.
- Local validation can verify config parsing, imports, and Docker build, but cannot prove live managed service connectivity without actual Railway-provided `DATABASE_URL` and `REDIS_URL`.

Implementation completed:

- `Settings.database_url` accepts `DATABASE_URL`.
- `Settings.redis_url` accepts `REDIS_URL`.
- Production still rejects missing PostgreSQL/Redis and rejects SQLite.
- Test coverage verifies Railway alias handling.

Evidence:

- `tests/api/test_api.py::test_production_settings_accept_railway_database_and_redis_aliases`
- Local Railway-style settings validation succeeded with `DATABASE_URL` and `REDIS_URL`.

Remaining gap:

- Run migrations and RQ queue operations against real Railway managed PostgreSQL and Redis.

### P0: OAuth provider callbacks require final deployed URLs and credentials

Root cause:

- OAuth callback URLs are generated from `REPOMIND_PUBLIC_APP_URL`.
- CORS accepts `REPOMIND_FRONTEND_ORIGIN`.
- GitHub/Google client IDs and secrets are not stored in the repository.

Implementation completed:

- OAuth routes and state storage exist.
- The deployment environment list below names the required variables.

Evidence:

- `backend/repomind/main.py` defines OAuth login and callback routes.
- `backend/repomind/core/auth.py` requires provider client IDs/secrets.

Remaining gap:

- Configure OAuth providers with the Vercel production URL and Railway backend URL, then validate end-to-end login on deployed infrastructure.

### P1: Backend image is large because analysis scanners are bundled

Root cause:

- Semgrep, Chroma, and analysis dependencies are large.

Implementation completed:

- Removed LLM extras from the backend Docker image.
- Added `.dockerignore` to prevent runtime/build artifacts from being sent as Docker context.

Evidence:

- Docker context dropped to 327.1 MB.
- `docker build -f Dockerfile.backend -t repomind-backend:railway-check .` succeeded.
- Container contains `bandit` and `semgrep`.

Remaining gap:

- Consider separate scanner worker images or pinned dependency constraints if Railway build time or image size becomes operationally expensive.

### P1: Trivy is optional and not installed in the backend image

Root cause:

- The scanner attempts Trivy only if the external binary exists.
- `Dockerfile.backend` installs Python analysis dependencies but not the Trivy binary.

Implementation completed:

- Bandit and Semgrep execution are present in the built image.

Evidence:

- Container command lookup found `/usr/local/bin/bandit` and `/usr/local/bin/semgrep`.

Remaining gap:

- Install Trivy in the worker image if dependency/container vulnerability scanning is required at launch.

### P2: Local model inference is disabled for Railway

Root cause:

- Railway config sets `REPOMIND_ENABLE_MODEL_INFERENCE=false`.
- The backend image intentionally excludes LLM extras.

Implementation completed:

- Chat has deterministic fallback behavior when local model initialization fails.
- Railway config avoids unsafe remote model code by setting `REPOMIND_TRUST_REMOTE_MODEL_CODE=false`.

Remaining gap:

- If paid/local model inference is required in production, use a separate model-serving service or a larger worker image.

## Deployment Order

1. Create Railway project.
2. Add Railway managed PostgreSQL.
3. Add Railway managed Redis.
4. Deploy backend API from `Dockerfile.backend` using `deploy/railway.toml`.
5. Set backend production secrets and URLs.
6. Confirm `alembic upgrade head` runs against Railway PostgreSQL.
7. Deploy worker from the same image using `deploy/railway.worker.toml`.
8. Confirm worker connects to Railway Redis and sees the `repomind-analysis` queue.
9. Attach and validate a durable artifact strategy for reports, Chroma, uploads, and indexes before using separate backend and worker services.
10. Deploy frontend to Vercel.
11. Set `NEXT_PUBLIC_API_BASE` or `NEXT_PUBLIC_API_BASE_URL` to the Railway backend URL.
12. Set OAuth provider callback URLs to:
    - `https://<railway-backend-domain>/auth/github/callback`
    - `https://<railway-backend-domain>/auth/google/callback`
13. Validate signup, login, repository import, analysis, report download, and chat on deployed infrastructure.

## Final Answer

Can RepoMindAI be deployed on Vercel + Railway today?

NO.

Exact remaining launch blockers:

1. Separate Railway backend and worker services do not have a proven shared artifact store for worker-generated reports, Chroma indexes, uploads, exports, and index manifests.
2. Railway managed PostgreSQL and Redis connectivity has not been validated against live Railway credentials.
3. OAuth callbacks cannot be proven until final Vercel/Railway domains and provider credentials are configured.
